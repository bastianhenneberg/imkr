Agents

Every pane running a coding agent shows what it is doing: ● working, ◆ blocked (it waits for you), ✦ done (finished while you were elsewhere), ✓ idle or ✗ failed (its turn ended in an error: a used up limit, a refused login, an API error; magenta, with the reason). A window tab turns red when an agent there waits or failed, the bell rings, and Ctrl+B a takes you to it. An agent counts as failed when its StopFailure hook says so, or, without hooks (Codex), when it is quiet for 5 seconds with an error like „usage limit“ or „API Error“ at the bottom of its screen. You also get a desktop notification when an agent waits or finishes while you look elsewhere or are detached: through notify-send, or as OSC 9 for terminals like Ghostty and WezTerm, or not at all (setting notifications = "system" | "terminal" | "off").

imkr recognises claude, codex, opencode, aider, gemini, crush, goose, amp, cursor-agent, qwen, kilo and pi. It guesses from their output and from questions on the screen. Other agents and their questions go into the config (extra_agents = ["my-agent"], question_phrases = ["Proceed now?"]), and imkr explain --pane N says why a pane counts as the agent it is, in its state, or as none. For exact states, let the agent report them with hooks. For Claude Code:

imkr hooks --install    # puts them into ~/.claude, on every machine you run agents on
imkr hooks              # or just prints them for ~/.claude/settings.json

--install writes ~/.claude/hooks/imkr-agent-state.sh, adds its hooks to ~/.claude/settings.json next to your other hooks (backed up as settings.json.bak-imkr, imkr's own from before replaced), and works where ~/.cargo/bin is only on interactive shells' PATH. Waiting is reported both by permission requests and, for agents running with permissions skipped, by the notification that a question waits. Agents started after it report their state. Where pi is set up (~/.pi/agent), --install also puts an extension into its extensions that reports pi's state the same way: working while it runs, done after its turn, waiting when an error stays after pi's own retries.

The hooks call imkr status working|blocked|idle|clear, which knows its pane from $IMKR_PANE and does nothing outside imkr. It reads the hook's JSON from stdin: a subagent finishing does not mark the agent done, and the session id is kept to resume the agent later. The transcript's path comes along too: imkr reads the model and context of the agent's last answer from its end and shows them as opus 5.5 · 300k in Ctrl+B A, the inbox, imkr agents and, for the focused agent, in the sidebar.

What an agent says it is doing shows under it in the sidebar, after it in Ctrl+B A and in imkr agents, on every machine: the title it gives its terminal. Claude Code keeps a short summary of its task there; spinners in front are cut off, and a title that only names the program is left out.

Scripts and agents can drive imkr too:

imkr list [--json]                        # panes with program, state and directory
imkr send --pane 3 "run the tests"        # type into a pane, then Enter
imkr new --window 2 -- claude --resume    # start a command in a new pane
imkr new --float                          # a floating shell
imkr rename "tests"                       # name the pane this runs in
imkr wait --pane 3 --until ready          # wait until an agent is idle or done
imkr read --pane 3 --lines 20             # what it wrote last
imkr rename --window 2 api                # name a window
imkr notify "tests are green"             # a notification, titled after this pane
imkr notify --title build "done in 42 s"  # with a title of its own

notify goes out the way the settings say (a desktop notification through notify-send, OSC 9 to the terminal, or none) and shows up in the control bar as well.

Several accounts, and the next one when one is used up

One machine, several Claude Code and Codex subscriptions, and providers Claude Code reaches by address and key (OpenRouter, a local Ollama). Each account is an environment the agent starts with: a subscription gets a directory of its own (CLAUDE_CONFIG_DIR, CODEX_HOME) holding only its login, and everything else links to ~/.claude or ~/.codex, settings, hooks, skills, MCP servers and the conversations. So a conversation goes on in another account where it stopped. ~/.claude itself is the account standard.

imkr account add claude privat          # logs it in: Claude Code starts in it, /login, /exit
imkr account add codex work             # `codex login` in it
echo "$KEY" | imkr account add claude router --url https://openrouter.ai/api \
                                             --model qwen/qwen3-coder --token-stdin
imkr account add claude local --url http://localhost:11434 --token ollama --model qwen3-coder
imkr account                            # every account, in the order to fall back in
imkr account use privat                 # new shells of this session start in it
imkr account switch privat --pane 3     # the agent in pane 3 goes on in it, now
imkr account run privat -- claude       # one command in it
imkr account sync                       # share what is new in ~/.claude, MCP servers again
imkr account default henneberg          # new shells on this machine start in it

Accounts show by the subscription they are logged in to, (standard) marks the one new shells start in (imkr account default, else ~/.claude), and commands take either name: imkr account use stelljes finds standard when that is stelljes' login. A pane keeps the account it started in, also when the default changes later. imkr settings sync brings the list of accounts to the other machines, without logins: log in there once with imkr account login NAME.

Every agent's frame says what it runs on, after its state: claude ● working · henneberg · opus 5.5 (the subscription by its address before the @, then the model), or · Ollama · qwen3-coder for a provider.

Ctrl+B k starts an agent and asks which account it runs in: every account of Claude Code and Codex (those installed), logged out ones marked, the default selected; Enter or its number starts it. With only one account logged in, it starts right away. It starts in the focused pane, or in a new pane beside it when a program runs there; p in the list switches to a new window instead (until imkr ends). new_agent_in = "window" in the config makes the new window the default. What it starts is [agent_commands] in the config, else the agent's name:

[agent_commands]
claude = "claude --dangerously-skip-permissions --chrome"

The same command starts wherever an agent is written as a placeholder: <claude> in a session template, in imkr new -- '<claude>' … and imkr worktree NAME -- '<codex>', and in imkr fleet --agent claude. <agent> stands for default_agent (claude unless the config says otherwise), and <claude@work> starts it in the account claude:work right away instead of asking. Each machine fills in its own [agent_commands], and a template saved from a running session writes its agents this way.

Ctrl+B s c lists them: Enter puts the focused agent into the chosen account, u new shells of this session. Switching ends the agent and starts it again in the same conversation, typed into its shell as imkr account run claude:privat -- claude --resume <id>, so no key shows on the screen; the session id comes from the hooks.

When an agent says its account is used up ("5-hour limit reached ∙ resets 7pm", Codex: "You've hit your usage limit"), imkr notes that account as used up until then and, as Account used up in the settings says, tells you which account is next (ask, the default), goes on in it by itself (auto), or does nothing (off). The next one is the next in the list that is logged in and not used up, round. Accounts and keys live in ~/.local/state/imkr/accounts/ (0600).

Limits belong to the subscription, not to the account's name. imkr account shows who each one is logged in as, and add and login warn when an account is logged in to a subscription that has one already; nothing is removed for it. One used up counts for every account of the same subscription, so falling back never lands in the same limit.

A login Claude Code has emptied, because the server refused its refresh token, shows as logged out, also for ~/.claude (imkr account login claude:standard logs it in again). Such an account is no subscription: it is not counted twice, not fallen back to, and new shells do not start in it: when the default is logged out, they start in the first account that is logged in. A pane whose account is logged out starts in the default when it comes back.

One person is one account. imkr account add claude stelljes again logs stelljes in anew instead of failing, and so does adding a name a logged out account was logged in as. When the browser login of a new account turns out to be a person another account was or is logged in as, the login moves into that account and the new one goes again (unless agents run in it already). A logged out account whose person is logged in elsewhere, such as an old ~/.claude, is left out of the lists.

A Claude login lasts about 30 days from /login; Claude Code renewing its key does not move that end. So imkr says it ahead: three days before, imkr account and the account lists show login ends …, and one imkr on the machine sends a notification once, as it does when a login is logged out, each with the imkr account login that logs it in again.

Claude's numbers are those of Claude Code's /usage, asked of Anthropic with the account's login. A local Ollama has no limit.

Agents talking to each other

Agents in imkr can find, read and message each other, on this machine and on the others:

imkr agents --all                                  # every agent with its address
imkr msg server:api/claude "The API returns 409 on duplicates now, please update the client."
imkr msg --wait api/3 "Which port does the dev server use?"   # waits, prints its screen
imkr msg server:api/claude < handover.md                       # a long text from stdin

An address is machine:session/pane; in the own session a pane number, name or program is enough. imkr types the message in once the agent is idle, one at a time, never while it works and never into a question it asks, which stays yours. Each message says who sent it and how to answer. imkr skill prints the guide for agents, imkr skill --install puts it into Claude Code's skills, so the agents use it on their own. imkr read server:api/3 shows another agent's screen, on any machine.

Answers find their way back without every machine reaching every other: a server needs no ssh to your laptop. A message for a machine out of reach waits in the sender's outbox (imkr outbox), and the machine it is for picks it up when it next asks that one, every 5 seconds while its imkr runs, so a laptop that was offline gets it later.

Other people's imkrs

Colleagues with their own imkr (their machine, their Claude account) can message your agents, and you theirs, without ssh to each other's machines. Pair once, both sides turn on the web view (web = true) in a VPN such as NetBird or Tailscale:

imkr connect invite                                 # you: prints a code, good for 10 minutes
imkr connect join http://100.97.1.2:4657/ ABCD-EFGH # they: what invite printed
imkr msg martin:api/claude "Can you look at the login bug?"

Without a common network, AI Brain carries the messages: it knows the people and who may write to whom, imkr goes through ai-brain-harness (connected with ai-brain-harness connect) and signs in nowhere itself.

imkr connect brain martin                           # both sides, each with the other's name
imkr msg martin:api/claude "Can you look at the login bug?"

Every imkr with such a contact asks AI Brain every 30 seconds while it runs (imkr connect fetch does it now).

A contact's name is the machine part of an address. Their messages wait until you accept them: imkr connect inbox, accept ID, decline ID, or Ctrl+B i. imkr connect trust NAME types them in right away like your own, untrust asks again, rm NAME ends it. A contact can only send messages: no screens, no keys, no shell. Answers go back the same way, the message says how.

MCP

imkr mcp serves the same as tools over MCP on stdin/stdout: imkr_agents, imkr_panes, imkr_read, imkr_send, imkr_message, imkr_run, imkr_wait and imkr_new_pane. Each runs imkr's own command, so addresses on other machines work as on the command line, and text never goes through a shell. For Claude Code:

claude mcp add imkr -- imkr mcp

Started in an imkr pane, the server knows its session and pane by itself.

tmux for agent teams

Programs that drive tmux, like Claude Code's agent teams, can open imkr panes instead. Turn on tmux for agent teams in the settings: panes started after that find imkr as tmux on their PATH, with $TMUX and $TMUX_PANE set, and split-window, new-window, send-keys, capture-pane, kill-pane, display-message, list-panes, list-windows, select-pane and rename-window work on imkr panes (%3 is pane 3); layout and option commands are accepted and do nothing, kill-session and kill-server are refused. It is off by default, since programs that see $TMUX act as if inside tmux. Tested with scripts that use these commands, not yet with every program that drives tmux.

Running commands in a pane

With shell integration (OSC 133), imkr knows where a command's output starts and ends and how it ended. Many prompts send it already; otherwise add one line to the shell's rc file:

eval "$(imkr shell-integration zsh)"   # or bash; does nothing outside imkr

Then a script or an agent can use a shell in another pane like its own:

imkr run --pane 3 -- cargo test   # types it in, waits, prints the output, exits with its code
imkr wait --pane 3                # waits for the command running there (--timeout S)

Where the user sits

An agent on another machine sometimes wants to show you something on your own screen, a browser for example. imkr operator says which machine you sit at, as the terminal attached to the session tells it:

imkr operator          # laptop
imkr operator --json   # {"machine": "laptop", "via": "codingmachine", "here": false}

via is the name your machine reaches this one by, e.g. for a tunnel back. If nobody is attached to the agent's session, it asks the other sessions on the machine; with nobody anywhere it fails. AI Brain's agent-tunnel uses it to open its browser where you are.

Copying files

imkr cp copies like scp, and also to and from the directory a pane works in, here or in another session or on another machine:

imkr cp notes.md @3                     # into pane 3's directory
imkr cp report.pdf @server:api/claude   # into the directory of claude in session api on server
imkr cp @api/claude::target/out.log .   # a file below that pane's directory, here

Events

imkr subscribe prints what changes in the sessions on this machine, one JSON object per line, for scripts, status bars and agents that wait for each other (-s NAME watches one session, --snapshot lists every pane first):

{"event":"state","session":"api","pane":1,"program":"claude","window":2,"from":"working","state":"blocked","time":1791843836}

Events are state (an agent's state changed, null without one), pane-opened, pane-closed and pane-moved (to another window, with from_window).
